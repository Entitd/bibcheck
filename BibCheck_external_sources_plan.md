# BibCheck: новые источники и план реализации внешней проверки

Дата: 13 октября 2026 года.

Проект: https://github.com/Entitd/bibcheck

План составлен по коду коммита `b3fafb79e11053b10b1edec593d66a8fcee7b5ac`. Это техническое задание на доработку, а не описание уже реализованного функционала. Примеры новых классов, таблиц, маршрутов и форматов ниже — предлагаемые решения.

## 1. Цель и границы

Добавить проверку существования публикаций и правильности библиографических данных через несколько внешних баз. Проверка должна работать на сервере без регистрации пользователя во внешних сервисах, без ввода его почты и без обязательных персональных API-ключей.

Основной набор: **Crossref, Open Library, DataCite, DBLP**. OpenAlex сохранить как дополнительный источник с серверным ключом. Europe PMC и arXiv подключить вторым этапом при необходимости тематического покрытия.

Подтверждать нужно название, авторов, год, идентификаторы и сведения об издании. Наличие записи в базе не доказывает истинность научных выводов; отсутствие записи не доказывает, что источник выдуман. Проверку ГОСТ и требований кафедры сохранять отдельной от внешнего поиска.

Ограничения реализации:

- Laravel 12, PHP 8.2+, Inertia + React; использовать уже имеющиеся HTTP Client, Queue, Cache и Eloquent.
- Не добавлять библиотеки для каждого API и не скачивать полные тексты/PDF ради проверки метаданных.
- Контроллеры принимают запрос и возвращают результат; выбор баз, сравнение и агрегация находятся в сервисах.
- Параметры API задаёт администратор сервера. Пользователь нажимает «Проверить источники» и получает результат.

## 2. Источники первого этапа

Лимиты проверены по официальным источникам в день составления плана. В эксплуатации учитывать заголовки ответов и HTTP 429: сервисы могут менять условия.

| Приоритет | База | Назначение | Доступ | Лимит и рекомендуемая стартовая настройка |
| --- | --- | --- | --- | --- |
| 1 | Crossref | Статьи, конференции, книги и главы с DOI | Без ключа; служебный email приложения через `mailto` | Поиск: 1 запрос/с анонимно, 3/с с email. Одна запись: 5/с и 10/с. Параллельность public/polite: 1/3. На старте приложения: 1 запрос/с, один запрос одновременно |
| 2 | Open Library | Книги по ISBN и по названию/автору; конкретные издания | Без регистрации и ключа | 1 запрос/с; 3/с с идентифицирующим User-Agent и email. На старте: 1 запрос/с |
| 3 | DataCite | Датасеты, ПО, диссертации, отчёты, материалы репозиториев с DOI | Без ключа для чтения; служебный email в User-Agent или `mailto` | 500 запросов/5 минут на IP; 1000 с идентификацией. На старте: 1 запрос/с и не более 450/5 минут |
| 4 | DBLP | Информатика, конференционные и журнальные публикации | Без ключа | Универсальная численная квота не подтверждена. Начать с 1 запроса/с как собственного ограничения, учитывать 429 |

Служебная почта — реальный контакт разработчика/администратора BibCheck, единый для приложения. Почту посетителя не передавать. Использование разных email/IP для обхода ограничений не предусматривать.

### 2.1. Crossref

Базовый URL: `https://api.crossref.org`.

- DOI: `GET /works/{doi}`. DOI передавать как корректно закодированную часть пути; не удалять его внутреннюю пунктуацию.
- Поиск: `GET /works` с `query.bibliographic`, при наличии `query.author`, `rows=5`, `mailto`.
- Из ответа использовать DOI, title, author, published/issued, container-title, publisher, volume, issue, page, ISBN/ISSN и связи обновлений.
- `created` — дата создания записи в Crossref, а не год публикации. Не использовать её как резервный год издания.
- При известном DOI сначала получать запись по DOI; искать по названию только при отсутствии результата или для диагностики несовпадения.

В проекте уже есть `OpenAlexProvider::searchCrossref()`, но метод не вызывается. Перенести полезную логику в отдельный `CrossrefProvider`, а не добавлять новые API внутрь OpenAlexProvider.

### 2.2. Open Library

Базовый URL: `https://openlibrary.org`.

- ISBN: `GET /isbn/{isbn}.json` — запись конкретного издания.
- Поиск: `GET /search.json` с `title`, `author`, `limit=5` и выбранными полями.
- Для издания получать название, ISBN, издательство, дату издания и авторов. Если авторы представлены ссылками, запрашивать их карточки только при необходимости и кешировать отдельно.
- Для каждого дополнительного HTTP-запроса, включая карточки авторов, соблюдать общий лимит.
- Различать `work` и `edition`: год первого издания произведения не подтверждает год указанного перевода или переиздания.
- Если найдено произведение, но конкретное издание не установлено, возвращать частичное подтверждение.

Не строить новую интеграцию вокруг legacy `/api/books`: официальная документация рекомендует Search API и отдельные Works/Editions/ISBN API.

### 2.3. DataCite

Базовый URL: `https://api.datacite.org`.

- DOI: `GET /dois/{doi}`.
- Поиск: `GET /dois` с `query`, например `titles.title:"НАЗВАНИЕ"`, и `page[size]=5`.
- Использовать JSON:API: запись находится в `data.attributes`, результаты поиска — в массиве `data`.
- Нормализовать titles, creators, publicationYear, publisher, types, identifiers, relatedIdentifiers и URL.
- Экранировать пользовательский текст для синтаксиса поисковой строки отдельно от URL-кодирования параметров.
- Для поиска без DOI DataCite включать прежде всего для данных, ПО, диссертаций и отчётов. Для точного DOI тип BibLaTeX не должен мешать проверке.

### 2.4. DBLP

Базовый URL: `https://dblp.org`.

- Поиск публикаций: `GET /search/publ/api` с `q`, `format=json`, `h=5`.
- Разбирать `result.hits.hit[].info`: title, authors, year, venue, doi, url, type.
- Нормализовать форму authors: ответ может содержать одного автора или список.
- Идентификатор DBLP сохранять отдельно от DOI.
- Поиск в DBLP выполнять после неудачного универсального поиска для научных статей/конференций либо в явно выбранном профиле «Информатика».
- В обычном BibLaTeX-файле предметная область неизвестна: не считать любую `article` публикацией по информатике.

## 3. Дополнительные возможности

### OpenAlex — существующий источник

Сохранить, но изменить роль: дополнительный поиск и получение метаданных по DOI. Использовать серверный `OPENALEX_API_KEY`; не зависеть от `auth()->user()` в провайдере.

По актуальной документации бесплатный ключ даёт $1 API-бюджета в день: примерно 1000 обычных поисков или 10 000 list/filter запросов, до 30 запросов/с. Получение одной сущности по ID/DOI не расходует этот бюджет, но ограничение скорости сохраняется. При отсутствии ключа квота меньше; основной набор новых баз должен работать независимо от OpenAlex.

Один источник в текущей реализации иногда требует двух поисков. Не считать бесплатную квоту равной числу проверенных записей. Считывать использование/остаток бюджета из ответа, при исчерпании отключать затратный поиск до сброса квоты. Не оформлять платное пополнение автоматически.

### Отозванные публикации

Проверять доступные связи отзыва/исправления в Crossref. Данные Retraction Watch доступны через Crossref API и выгрузку. Отдельный аккаунт пользователя не нужен.

- Проверка существования и признак отзыва — независимые поля: публикация может существовать и быть отозванной.
- Разбирать направление связи и её тип. Не считать любой `update` отзывом: это может быть исправление или другое уведомление.
- Сохранять источник признака, дату проверки и ссылку на уведомление.
- Если сведений нет, писать «сведений об отзыве не найдено», а не гарантировать отсутствие отзыва.
- Для MVP использовать сведения API; полную локальную базу Retraction Watch подключать отдельным этапом при необходимости.

### Второй этап: Europe PMC и arXiv

| База | Когда включать | API и лимиты |
| --- | --- | --- |
| Europe PMC | PMID/PMCID/биомедицинский профиль | `https://www.ebi.ac.uk/europepmc/webservices/rest/search`, query, format=json; 10 запросов/с и 500/мин на IP. Начать с 1/с |
| arXiv | arXiv ID либо профиль математика/физика/информатика | `https://export.arxiv.org/api/query`, id_list или search_query; один запрос/3 секунды и одно соединение. XML/Atom |

Препринт отличать от опубликованной журнальной версии. Результат репозитория не должен автоматически подтверждать журнал, том и страницы финальной статьи.

Semantic Scholar, Google Books, издательские API и российские площадки не входят в обязательный первый этап: они требуют дополнительной настройки доступа, имеют менее удобные условия или неподтверждённый публичный API. Их можно добавить позже через тот же контракт провайдера.

Классы регистрировать/внедрять через Laravel Container. Провайдеры не должны читать текущего пользователя, сессию или выполнять запись в историю.

Минимальная схема контракта (псевдокод сигнатур, детали DTO уточнить при реализации):

```php
interface BibliographicProvider
{
    public function name(): string;
    public function supportsIdentifier(string $kind): bool;
    public function findByIdentifier(string $kind, string $value): ProviderResult;
    public function search(SourceQuery $query): ProviderResult;
}
```

Точное сравнение выполняет SourceMatcher, а не каждый провайдер по собственному порогу. Провайдер возвращает до пяти кандидатов и нормализованные метаданные.

## 6. Алгоритм проверки одной записи

### 6.1. Нормализация

- Сохранить исходные поля для отображения; создать отдельное нормализованное представление.
- DOI: удалить известный префикс `doi:`/`https://doi.org/`, лишние внешние пробелы; сохранить суффикс целиком. Проверка формы DOI не подтверждает регистрацию.
- ISBN: удалить разделители, проверить контрольную сумму ISBN-10/ISBN-13; учитывать X в ISBN-10. Допускается нормализация между эквивалентными ISBN-10/13.
- Название: Unicode, регистр, повторные пробелы, внешние LaTeX-скобки и известные команды оформления/акценты. Не уничтожать значимую математику и не стирать все команды вслепую.
- Авторы: разделитель BibLaTeX `and`, формы «Фамилия, Имя» и «Имя Фамилия», групповые авторы. `others` не является фамилией.
- Год брать из year или date; если они противоречат друг другу, сохранить отдельное локальное предупреждение.
- Тип брать из BibEntryDTO, а не угадывать только по полям.
- Поддерживать eprint/eprinttype/archiveprefix для будущей проверки arXiv.

### 6.2. Маршрутизация

| Условие | Порядок |
| --- | --- |
| Есть DOI | Crossref по DOI → при отсутствии DataCite по DOI → при необходимости OpenAlex по DOI |
| Есть ISBN / book / mvbook | Open Library по ISBN → поиск конкретного издания по названию/автору |
| article / inproceedings / proceedings без DOI | Crossref → OpenAlex при доступной квоте → DBLP как дополнительный поиск |
| incollection / inbook | DOI, если есть; затем Crossref по названию главы. Open Library может подтвердить только родительскую книгу |
| dataset / software / thesis / report без DOI | DataCite → OpenAlex при доступной квоте |
| online / misc без пригодных идентификаторов и метаданных | not_checkable либо ограниченный поиск при достаточных полях; не объявлять запись несуществующей |

Результат `not_found` в одной базе запускает следующую. 429/5xx не является `not_found`: допускается переход к другой базе, но итоговый результат должен отмечать неполноту проверки.

Не опрашивать все базы для каждой записи. Начальный бюджет: максимум 6 реальных HTTP-запросов на запись, до 5 кандидатов за поиск. Это собственные ограничения приложения, а не квоты сервисов. Если бюджет исчерпан до завершения цепочки, вернуть `incomplete`, а не `not_found`.

Если получена точная запись по идентификатору, прекратить поиск этой идентичности и перейти к сравнению полей. Если DOI принадлежит другой работе, показать расхождение. Поиск по названию может предложить правильный DOI, но не должен молча скрыть ошибочный DOI пользователя.

### 6.3. Сопоставление

Не использовать сходство названия как единственный критерий. Правила первого этапа:

1. Точный идентификатор + совпадающие заполненные поля → `verified`.
2. Точный идентификатор + противоречащие поля → `mismatch`, с перечнем различий.
3. Без идентификатора: сильное совпадение названия + совпадение авторов + совместимый год + явное преимущество над вторым кандидатом → `verified`.
4. Недостаточно метаданных для строгого вывода → `partial_match`.
5. Два близких кандидата или конфликтующие свидетельства → `ambiguous`.
6. Все запланированные пригодные базы успешно обработаны, кандидатов нет → `not_found`.

Сходство названия можно вычислять на нормализованных словах вместе с текущим similar_text. Не отображать его как вероятность достоверности. Порог и разрыв между первым/вторым кандидатом должны быть конфигурируемыми и проверенными на наборе реальных записей.

Год online-first и печатного выпуска может отличаться: учитывать известные даты отдельно. Разница ±1 — причина объяснить различие, а не автоматически подтвердить любую запись. При отсутствии года в ответе нельзя утверждать, что год пользователя проверен.

Издательство, журнал, том, номер и страницы проверять, когда база предоставляет подходящие поля. Отсутствующее поле — `unavailable`; несовпадающее — `different`. Препринт и финальная статья, произведение и издание, книга и глава требуют отдельных правил.

Несколько баз могут использовать одни и те же исходные данные. «Найдено в трёх базах» не должно автоматически означать три независимых подтверждения.

## 7. Единый формат результата

Сохранить ключ `api_check` для минимизации изменений, но добавить `schema_version=2`. Обновить PHP и TypeScript одновременно.

Ниже пример структуры для тестовой записи; значения не являются результатом реального запроса:

```json
{
  "schema_version": 2,
  "status": "mismatch",
  "found": true,
  "complete": true,
  "matched_by": "doi",
  "provider": "crossref",
  "similarity": 98,
  "external_title": "Example Article",
  "external_data": {
    "id": "provider-record-id",
    "doi": "10.0000/example",
    "title": "Example Article",
    "authors": [{"family": "Smith", "given": "John"}],
    "year": 2021,
    "container_title": "Example Journal",
    "url": "https://doi.org/10.0000/example"
  },
  "field_checks": {
    "doi": {"status": "equal"},
    "title": {"status": "equal"},
    "year": {"status": "different", "input": 2020, "external": 2021}
  },
  "candidates": [],
  "provider_checks": [
    {"provider": "crossref", "status": "found", "cached": false}
  ],
  "retraction": {"status": "unknown", "notice_url": null},
  "checked_at": "2026-10-13T18:30:00Z",
  "message": "Публикация найдена по DOI, но год отличается."
}
```

`found` означает, что идентичность источника найдена; это не флаг полной корректности. Для счётчика «Подтверждено» использовать `status === verified`. Из-за этого старый интерфейс, который красит всё по found, обязательно обновить.

Итоговые статусы:

| Статус | Значение |
| --- | --- |
| queued / checking | Ещё не завершена обработка |
| verified | Публикация найдена, предоставленные проверяемые данные согласуются |
| mismatch | Публикация найдена, есть расхождения |
| partial_match | Найдено частичное подтверждение |
| ambiguous | Несколько кандидатов или конфликтующие данные |
| not_found | Успешный поиск во всей выбранной цепочке не дал результата |
| not_checkable | Для этого типа/набора данных нет подходящей проверки |
| incomplete | Часть цепочки не выполнена из-за лимита, сбоя или бюджета запросов |
| invalid_input | Непригодный ввод, например ошибочная контрольная сумма ISBN |

Внутренние статусы провайдера: found, not_found, rate_limited, quota_exhausted, unavailable, unauthorized, malformed_response, skipped. Сохранять их отдельно от итогового статуса записи. Отзыв хранить отдельно: retracted / no_notice_found / unknown.

Не суммировать одну запись несколько раз, если она найдена в нескольких базах. Добавить verified_count, mismatch_count, partial_count, ambiguous_count, not_found_count, incomplete_count, not_checkable_count. Среднее сходство названий — дополнительная метрика, не общая оценка качества.

## 8. Очередь, данные и API

В проекте уже есть миграции jobs и cache. Для небольшого сервера начать с `QUEUE_CONNECTION=database`, `CACHE_STORE=database`. Redis не является обязательным для первого этапа; при росте нагрузки можно сменить драйверы, сохранив контракты.

### 8.1. Хранение запуска

Предлагаются две таблицы, чтобы воркеры не перезаписывали одновременно большой JSON истории:

**external_check_runs:**

- id: UUID;
- user_id: FK на users; текущий гостевой пользователь тоже имеет владельца;
- check_history_id: nullable FK, если запуск связан с сохранённой историей;
- content_hash, algorithm_version;
- status: pending / running / completed / failed / cancelled;
- input_analysis: JSON со снимком локального анализа и исходных записей;
- total_entries, finished_entries;
- created_at, updated_at, started_at, finished_at.

**external_check_entries:**

- id;
- run_id: FK на external_check_runs;
- entry_key, position, input: JSON с type/fields;
- status: queued / checking / completed / failed;
- result: JSON в формате раздела 7;
- checked_at, timestamps;
- уникальный индекс run_id + entry_key, если парсер гарантирует уникальность ключей.

Одинаковые ключи BibLaTeX сейчас могут конфликтовать с хранением entries в ассоциативном массиве. Перед созданием запуска обнаруживать дубли и возвращать локальную ошибку; не терять запись незаметно.

Статус completed у задания означает, что результат сохранён; внутри result может быть incomplete. Статус completed у запуска означает завершение обработки всех записей, а не подтверждение всех источников.

Для retry одного задания сохранять результат атомарно. При первом переходе записи в терминальное состояние увеличивать finished_entries в той же транзакции. Повторное выполнение не увеличивает счётчик повторно. Не держать транзакцию БД во время сетевого запроса.

Если user/run удалён или запуск отменён, задание прекращается. При сохранении результата повторно проверять актуальность запуска. Итоговый analysis_data для истории собирать из записей после завершения; если check_history_id задан, проверять владельца и соответствие снимка содержимому истории.

### 8.2. Запуск

1. Пользователь нажимает проверку.
2. FormRequest проверяет размер, число записей и допустимые параметры.
3. Сервер выполняет localCheck(), создаёт неизменяемый снимок и запуск.
4. Для каждой пригодной записи отправляет VerifyBibliographyEntry в очередь external-checks после commit.
5. Возвращает 202 + run_id или Inertia redirect на редактор с запуском.
6. React опрашивает прогресс раз в 2–3 секунды; по завершении прекращает polling.

Новые маршруты для сессионного интерфейса разместить в routes/web.php под auth, CSRF и throttle:

```text
POST /bibliography/external-checks
GET  /bibliography/external-checks/{run}
POST /bibliography/external-checks/{run}/cancel
```

Ввести StartExternalCheckRequest, ExternalCheckController, ExternalCheckResource и Policy владельца запуска. UUID не заменяет авторизацию. Сессионный гость использует существующий механизм гостевого пользователя; ему не нужно создавать внешний аккаунт.

Публичные stateless API-маршруты в routes/api.php не защищены автоматически сессией web. Не добавлять туда чтение чужих запусков без отдельного решения авторизации. Для первого этапа использовать сессионные маршруты web; ограничения существующего API пересмотреть отдельно.

Существующие `/api/sources/verify`, `/api/bib/check-full`, `/api/bib/check-external` менять явно: сохранить временную совместимость для небольших синхронных запросов либо добавить версию асинхронного API. Не превращать прежний ответ 200 с анализом в 202 без обновления клиентов и тестов. Любой синхронный вариант должен использовать тот же общий лимитер.

### 8.3. Ограничение нагрузки приложения

Начальные собственные значения: не более 200 записей/запуск, 1 активный запуск на пользователя, ограничение размера текста 1 МиБ, максимум 6 HTTP-вызовов/запись. Подбирать по эксплуатации; это не ограничения провайдеров.

Одинаковый повторный запуск пользователя для того же content_hash и версии алгоритма возвращает текущий активный run_id. Не объединять пользовательские истории между владельцами, даже если метаданные кешируются глобально.

## 9. Лимиты, HTTP-ошибки и повторные попытки

Общий HTTP-клиент должен:

- Использовать HTTPS с проверкой сертификата; убрать `withoutVerifying()` из OpenAlexProvider. При ошибке сертификатов исправлять CA на сервере.
- Отправлять идентифицирующий User-Agent: `BibCheck/1.0 (mailto:реальный-контакт)`.
- Передавать query-параметры массивом Laravel HTTP Client, а не склеивать URL с пользовательским текстом.
- Использовать connectTimeout около 3 секунд и timeout около 8 секунд как стартовые настройки.
- Ограничивать число результатов и размер ответа, проверять JSON и ожидаемую структуру.
- Отдельно распознавать сетевые ошибки, 401/403, 404, 429 и 5xx. Пустой корректный поиск — not_found; неверный JSON — malformed_response.
- Не повторять 401/403 бесконечно; отключать проблемный источник/сообщать администратору.
- Учитывать Retry-After в секундах или HTTP-date, а также доступные заголовки квот.

Лимитер должен работать **перед каждым HTTP-вызовом** и быть общим для web и всех воркеров. Ключ ограничителя: provider + операция/пул + серверный ключ или контакт. У Crossref отличать поиск от DOI lookup; соблюдать и скорость, и параллельность.

Для старта на database cache использовать атомарные locks: под блокировкой резервировать время следующего запроса. Например, собственный интервал 1 секунда для Crossref/Open Library/DataCite/DBLP, 3 секунды для arXiv. Отдельно удерживать ограничитель одновременных запросов до завершения HTTP-вызова. TTL блокировки должен быть больше timeout клиента; освобождать в finally.

Обычного ограничения «60 в минуту» недостаточно для соблюдения «1 в секунду»: оно допускает всплеск. Для DataCite дополнительно нужен счётчик/скользящее окно 5 минут. Весь retry тоже расходует лимит и резервируется повторно.

Если слот занят, отложить job через release(delay), не удерживать PHP-процесс длительным sleep. Установить retryUntil для ограничения общего времени жизни задания и учесть, что release увеличивает число attempts. При повторном входе использовать кеш уже полученных ответов, чтобы не начинать весь поиск заново.

Для 429/5xx/сетевого сбоя предусмотреть ограниченные повторы с растущей задержкой, например 5/15/60 секунд, с учётом Retry-After. После исчерпания попыток вернуть incomplete и причины. Не кешировать ошибку как отсутствие источника.

Если OpenAlex исчерпал дневной бюджет, поставить общий cooldown до сброса. Остальные базы продолжают работать. Повторяющиеся сбои провайдера временно приостанавливают обращения к нему.

## 10. Кеширование

Кешировать ответы провайдера, а не окончательный вердикт для любого похожего названия. Это позволяет заново сравнить те же метаданные с другим годом/автором пользователя.

Предлагаемые TTL приложения:

| Данные | TTL |
| --- | --- |
| Метаданные по DOI/ISBN | 7 дней |
| Список кандидатов поиска | 24 часа |
| Успешный ответ «не найдено» | 6 часов |
| Отдельная проверка сведений об отзыве | До 24 часов |
| 429/временный сбой | Только короткий cooldown по заголовкам/политике, не отрицательный кеш |

Ключ содержит provider, operation, версию нормализации и hash нормализованного запроса. Для поиска в hash включать название, авторов, год, тип и другие влияющие фильтры. Для получения метаданных по ID достаточно нормализованного ID и параметров ответа.

Совпадающие одновременные запросы защищать cache lock; второй процесс использует готовый кеш либо откладывает задание. В cached результате сохранять исходный fetched_at и признак cached; не выдавать старую проверку за только что выполненную.

Хранить нормализованные публичные метаданные и короткую диагностическую информацию. Не сохранять API-ключи, заголовки Authorization и целые пользовательские файлы в общем кеше метаданных.

## 11. Конфигурация

Добавить `config/bibliography.php`: enabled-провайдеры, порядок цепочек, timeout, кеш, лимиты приложения и версия алгоритма. Контакты и секреты читать через config, не напрямую env() из сервисов.

Пример `.env`:

```dotenv
BIBCHECK_CONTACT_EMAIL=admin@your-real-domain.example
BIBCHECK_USER_AGENT="BibCheck/1.0"
BIBCHECK_EXTERNAL_ENABLED=true
OPENALEX_API_URL=https://api.openalex.org
OPENALEX_API_KEY=
QUEUE_CONNECTION=database
CACHE_STORE=database
```

Пример почты заменить реальным рабочим адресом. Если контакт не настроен, использовать анонимные квоты; не подставлять фиктивный email для повышенного лимита.

Для Crossref/Open Library/DataCite/DBLP никаких секретов создавать не нужно. OpenAlex без серверного ключа можно отключить в цепочке поисков; основной режим остаётся доступным.

В настройках профиля перестать требовать персональный ключ. Существующую колонку пользователя можно оставить для совместимости, но базовая проверка и job не должны её использовать. Не отдавать серверный ключ в React props или ответ API. Для серверного OpenAlex предпочтителен Authorization Bearer, если поддерживается, чтобы секрет не попадал в URL журналов.

## 12. Интерфейс и история

- Заголовок «Поиск в OpenAlex» заменить на «Проверка источников».
- Кнопка доступна без пользовательского ключа; показывать прогресс и возможность отмены.
- Для записи выводить состояние, использованную базу, способ совпадения, ссылку на найденную запись и время проверки.
- Расхождения представлять таблицей: поле / у пользователя / во внешней базе / результат.
- Для ambiguous показать до 3–5 кандидатов. Выбор пользователем не делать обязательным для автоматического режима; он служит способом разрешить неоднозначность.
- Исправления предлагать явно; не перезаписывать .bib автоматически.
- Ошибка провайдера и не найденная публикация должны иметь разные тексты.
- Показывать число подтверждённых, с расхождениями, неоднозначных и не проверенных записей.
- Сохранить результат локального анализа отдельно от внешней сводки.
- При изменении текста во время проверки результаты относятся к snapshot/content_hash. Не накладывать их на новую редакцию файла; сообщить, что проверялось предыдущее содержимое.
- Старые записи истории без schema_version читать как v1. Старый found по названию отображать как исторический результат OpenAlex, не превращать его в новое строгое verified.

В API Resource сохранять прежние поля там, где это возможно; новые поля добавлять с версией. Пересчитать ApiMetrics и BibEditorViewData, чтобы mismatch с found=true не попадал в «полностью подтверждено».

## 13. Проверки перед выпуском

Тестировать через Laravel Http::fake(), без расходования внешних квот. Обновить существующие `tests/Feature/ApiSourceTest.php` и `tests/Feature/ApiBibValidationTest.php` с учётом нового сервиса и совместимости.

Обязательные сценарии:

- Точный DOI и согласованные поля; точный DOI от другой публикации.
- Название одинаковое, авторы разные: не давать verified.
- Правильный ISBN, но другой год/перевод/издатель; ошибочная контрольная сумма ISBN.
- Нет title, но есть пригодный DOI/ISBN: проверка выполняется.
- Online-first и печатная дата; глава книги и родительская книга.
- OpenAlex недоступен/без ключа: новая цепочка работает.
- Crossref not_found → DataCite found; ошибка первой базы → результат другой с корректной полнотой.
- 429, Retry-After, 5xx, timeout, неверный JSON: никогда не превращаются в not_found.
- Два близких кандидата; отсутствие авторов/года в ответе.
- Отзыв против исправления; источник найден, но retracted.
- Кеш повторного запроса; author/year меняют поисковый ключ; смена алгоритма не использует старый вердикт.
- Конкурирующие jobs соблюдают лимит и не дублируют сетевой вызов/счётчик прогресса.
- Повторный submit не создаёт вторую активную проверку.
- Другой пользователь не читает/не отменяет запуск; гостевой владелец имеет доступ только к своим данным.
- Изменение текста не смешивает новый редактор и старые результаты.
- Отмена/удаление запуска, рестарт воркера, повторное выполнение и старый формат истории.

Провайдеры тестировать на небольших обезличенных JSON fixtures с реальными структурами ответов, включая неполные метаданные. Перед включением каждого провайдера провести несколько ручных smoke-запросов с сервера и проверить TLS, квоты и форматы. Пороги сопоставления оценить на наборе верных/ошибочных/неоднозначных записей, включая русские названия и транслитерацию.

## 14. Порядок реализации

1. Ввести DTO/контракт/нормализацию/новый результат и adapter v1; убрать зависимость провайдеров от auth().
2. Создать CrossrefProvider и OpenLibraryProvider; реализовать DOI/ISBN-first и сопоставление автора/года.
3. Подключить DataCiteProvider и DblpProvider, маршрутизацию по типу; добавить общий кеш и ограничение каждого HTTP-вызова.
4. Создать хранение запусков, job, авторизованные маршруты и polling. Массовую проверку включать только после этого этапа.
5. Обновить интерфейс, метрики, вердикты, историю и справку; убрать обязательность пользовательского ключа.
6. Добавить признаки отзыва через Crossref; затем Europe PMC/arXiv по потребности.
7. Выполнить тесты, сборку и серверные smoke-проверки; проверить потребление квот на файле из 50–100 записей.

Минимальный рабочий выпуск включает четыре базы, очередь, кеш, лимитер и корректные статусы. Новые базы без исправления сравнения названий и без контроля массовых запросов не считать завершённой реализацией.

## 15. Запуск на сервере

После реализации и миграций использовать текущую БД приложения. В проекте уже есть миграции jobs/cache, не создавать их повторно. Для production нужен постоянный queue worker через systemd/Supervisor; `composer run dev` не заменяет его.

Пример команды воркера:

```bash
php artisan queue:work --queue=external-checks --sleep=1 --timeout=90 --tries=20 --max-time=3600
```

Это стартовые значения приложения. Заданию задать retryUntil, например 30 минут, чтобы многочисленные release() из-за лимита не делали его вечным. При клиентском timeout 8 секунд и бюджете 6 сетевых запросов 90 секунд дают запас, если внутри нет длительных sleep/немедленных многократных retry.

В `config/queue.php` настроить retry_after больше timeout воркера, например 150 секунд. TTL блокировок учитывать по назначению. На старте достаточно одного воркера; увеличение их числа не должно увеличивать фактическую скорость сверх общего лимитера.

Применение конфигурации после изменения `.env`:

```bash
php artisan migrate --force
php artisan config:cache
php artisan queue:restart
```

Команды выполнять как часть принятого процесса развёртывания. Настроить очистку старых запусков, результатов, failed jobs и гостевых данных. В логах хранить provider, status, latency, cache_hit и код ошибки, не секреты и не полный текст библиографии.

Нагрузка в основном сетевая: CPU/RAM расходуются на небольшой JSON и сравнение строк. Реальные возможности конкретного сервера определяются числом запусков, БД и квотами API; оценивать их по замерам, а не обещать мгновенную проверку любого объёма.

## 16. Критерии готовности

- [ ] Пользователь, включая гостя, проверяет файл без внешней регистрации, почты и API-ключей.
- [ ] Crossref, Open Library, DataCite и DBLP реально вызываются в подходящих цепочках.
- [ ] DOI/ISBN имеют приоритет, авторы и год участвуют в сравнении.
- [ ] Разные базы возвращают единый контракт; существуют объяснимые статусы и расхождения.
- [ ] Массовые запросы выполняются через очередь; web-запрос не ждёт проверки всего файла.
- [ ] Лимиты общие для всех пользователей/воркеров и всех повторных HTTP-вызовов.
- [ ] Есть кеш и корректная обработка временных ошибок/квот.
- [ ] Ошибка API не считается отсутствием источника или нарушением требований кафедры.
- [ ] Серверные ключи не попадают в браузер; TLS проверяется; запуски защищены владельцем.
- [ ] Старый анализ/история читаются, новая редакция текста не получает чужой снимок результатов.
- [ ] Повторы jobs, отмена и параллельное завершение не повреждают результаты/прогресс.
- [ ] Сборка фронтенда и смысловые тесты проходят; проведены реальные smoke-запросы с сервера.
